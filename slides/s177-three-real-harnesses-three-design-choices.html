III · Harnesses in the wild

Three real harnesses, three design choices

Systems · Constraints · Agents

Add-on · slide C1

The same five subsystems can be assembled very differently. Here is how three current open or semi-open harnesses do it.

Claude Code

Anthropic

Typed, async, repo-as-spec

QueryEngine class owns session state. Tools have a typed interface — compile-time safety. Async generator streams results turn-by-turn. Treats the repository as the system of record: AGENTS.md, SKILL.md files, verification commands. Strict permission system.

Hermes Agent

Nous Research (open source)

Synchronous, registry, self-improving

AIAgent class, synchronous loop. Tool registry pattern — runtime flexibility, plug-in tools without changing interfaces. Built-in learning loop: creates skills from experience, persists across sessions. Model-agnostic — any provider, any endpoint.

OpenClaw

Third-party Claude Code framework

Wrapper, orchestration-first

Wraps Claude Code's primitives to enable longer, more autonomous runs and richer orchestration. Common pattern in the ecosystem: take a vendor harness and extend it for workflows the vendor itself does not target. Trade-off: greater flexibility, but coupled to the upstream harness.

Different choices about state, tools, and skills — same five subsystems underneath.

The point is not which harness is best — it is that the same harness pattern admits many implementations. When PMs evaluate vendor agents or build their own, the questions to ask are about these design choices: how is state owned, how are tools registered, are skills first-class, is there a learning loop, what is the permission model.

These questions are answerable regardless of which harness someone is using or selling.
